# Архитектура Football Day

Сохраняем feature-first структуру Flutter и разделение domain → data → presentation. Новый сценарий находится внутри существующего `features/games`; перенос всех старых модулей не требуется.

## Поток данных

`FootballSchedule` строит детерминированные игры для даты. `FootballRepository` предоставляет поток заполненности и операции сохранения/отмены. Реализация Firestore объединяет готовое расписание с документами `footballBookings`. `FootballCubit` подписывается на выбранный день. Экран отображает состояние и передаёт намерение пользователя Cubit.

## Расписание без создания игр

Игра существует как комбинация времени и поля независимо от наличия документа в БД. Идентификатор: `<UTC epoch seconds>_<pitchId>`. Документ `footballBookings/{gameId}` — журнал бронирований готового слота, а не пользовательская игра. Он появляется при первой брони. Нет API создания/удаления/редактирования расписания.

## Атомарность

В одном документе находятся неизменяемые `startTime`, `pitchId`, карта `bookings` по Firebase UID и четыре счётчика `counts`. Операция в транзакции читает актуальный документ, учитывает прежнее число мест пользователя, проверяет вместимость и начало игры, затем заменяет его бронь и пересчитывает счётчики. При отмене удаляется только его запись.

Firestore Rules проверяют Google-авторизацию, расписание, неизменяемость метаданных, изменение только собственного UID, запрет прямого перехода в другую команду, точные дельты каждого счётчика, типы/длины имён и серверное время. Документ целиком удалять нельзя. Старый `/games` закрыт на запись.

Транзакции требуют соединения. Поток помечает кешированные данные; подтверждение показывается только после успешного коммита. При конфликте подписка обновляет свободные места, а UI сохраняет введённые данные для повторного решения пользователя.

## Масштаб и приватность

Один журнал ограничен максимум 24 участниками, поэтому карта в одном документе приемлема для этого формата. Журнал читается гостями: он содержит отображаемые имена, UID, команды и места; это публичный состав, не место для персональных контактов. Изменение этой политики требует отдельной модели публичного/приватного состава.

История после начала неизменяема. Удаление аккаунта требует сначала отменить будущие брони; исторические отображаемые имена не удаляются клиентом. Отдельная серверная процедура нужна для обезличивания исторических данных по запросу.
